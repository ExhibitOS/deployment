# Generic SSH lifecycle adapter

This source adapter implements a restricted public OED deployment plan and Manager lifecycle entry point. It does not claim a qualified Linux remote deployment or completed T10-02. The T10-01 Linux bundle and prepared remote runtime remain prerequisites; it does not upload artifacts, install an engine, provision a host, or create credentials.

## Prepared inputs

Use Node 24.21.0 on a Unix client with `/usr/bin/ssh`. The remote supported subset is an unprivileged account on Ubuntu 22.04 or 24.04, Node 24.21.0, a local Unix Docker endpoint, and already-present digest-pinned images. Place the approved executable Manager and private prepared bundle/runtime under the account's protected home. The normal local packager's exact nonzero lowercase `sha256:<64 hex>` content ID is accepted as an immutable local Runtime reference alongside repository@sha256 references; mutable tags are refused. Preserve that exact local ID rather than inventing a repository digest. The same unchanged reference is bound through OED, manifest, compose and Manager. The bundle must match the existing two-service self-host packaging contract exactly, including loopback port 13200, database and object/configuration volumes, image identities, labels and protocol. The wrapper does not substitute an unrelated bundle for an OED plan.

The OED selects an SSH private-key secret and database password secret through environment references or macOS Keychain references. Supply secret values through those providers, never the OED or command arguments. The database password must already match the prepared private `runtime.env` password and database URL. The wrapper resolves this credential transiently and compares its digest remotely; no credential value enters receipts. The SSH identity is written only into an owned temporary 0700 directory as an exclusive 0600 file, then removed after transport completion.

Create a private 0600 JSON connection file with exactly `consent`, `connection`, and `oed`. The connection has exactly `remoteRoot`, `managerPath`, `managerSha256`, `knownHostsPath`, `knownHostsSha256`, and `httpsOrigin`. Paths are absolute. Independently verify the server's host-key fingerprint before creating the dedicated canonical known-hosts file; do not accept an unverified scan. The client pins this file's approved SHA and checks identity before and after SSH. OpenSSH reads an exclusive 0600 copy of the verified bytes inside the owned temporary directory, so replacement of the original path during transport cannot select a different host-key file. Its path cannot contain whitespace, quotes, backslash or `%` expansion tokens. Manager SHA approval must come from the trusted release channel.

## Commands

Run `node bin/generic-ssh.mjs <command> /absolute/private/connection.json`.

- `plan` checks OS, protected paths, exact bundle and runtime binding, local engine and observed firewall policy. It makes no deployment changes. Its public receipt omits secrets and raw paths.
- `install`, `start`, `stop`, and `restart` obtain a fresh plan, bind unchanged remote input bytes and delegate to the existing Manager. Mutating commands require `consent: true`; volumes are preserved and installation uses only existing images. Repeating install for the identical already-installed bundle returns an idempotent result.
- `status` reports bounded Manager state and readiness; `logs` returns only up to 50 safe timestamp/code records, without raw messages or process output.
- `retry` delegates the last qualified failed/interrupted install/start/stop/restart job to the Manager's existing retry command. SSH interruption is uncertain and does not automatically replay an action.
- `verify` checks that manual DNS resolves to the SSH target and observes certificate-valid HTTPS readiness using the existing application protocol. DNS delay, TLS failure and unavailable health remain failures. Configure DNS and the HTTPS reverse proxy separately; this adapter does not rewrite DNS or TLS configuration.
- `rollback` consumes a fresh source plan and delegates the existing Manager full original-backup restoration into a fresh candidate. It requires an already enrolled signed Manager recovery authority in `recovery_required`, an authenticated original service backup, external writers quiesced and apps closed. It never reverses just an image. SSH interruption or incomplete restoration remains uncertain; do not automatically repeat the command.

For rollback only, add a top-level `rollback` object to the private connection file with exactly `profilePath`, `updatePath`, `updateSha256`, `keyPath`, `archivePath`, `maintenanceImage`, `operationId`, `expectedGeneration`, and `port`. Paths refer to existing remote files/directories in the protected account home; the key is an existing private 32-byte file outside the Manager profile, not a key value or client-uploaded credential. `updateSha256` pins the approved `exhibitos-update` executable supporting operation/generation-bound original rollback. `maintenanceImage` is a qualified local `sha256:<64 lowercase hex>` digest. The operation UUID and generation identify the current signed recovery intent; port must be an unused nonprivileged local port. The intent's original source root must exactly equal `connection.remoteRoot`. Existing install/start commands and their three-field connection files remain compatible.

The operation/generation-bound CLI implementation is pinned to Manager commit `a49769c6e7599082108eea98c468b6831108df2f` (merged by Manager PR #166), or a compatible main revision containing that change. Build and approve the executable for the actual remote Linux target and pin its own SHA; the locally checked macOS executable is not a Linux release artifact.

The remote adapter rechecks the ordinary source binding, approved update executable and protected key/archive. The Manager checks the exact operation/generation and RecoveryRequired stage under the same lock that registers, restores and activates the fresh candidate. Before returning completed, the adapter requires authenticated backup/inventory/image/schema receipts, the expected original health identity, a cold RolledBack intent, matching authority generation, the exact selected fresh candidate and actual candidate readiness. Public output contains safe IDs and verification booleans only, not keys, paths, hostnames, raw CLI output or runtime settings. TLS/firewall qualification stays separate; endpoint verification must still be run. Original data, failed candidates and immutable history are retained.

The adapter does not manufacture a signed recovery authority or claim that an unrelated standalone install can be rolled back through an existing signed plan. Prepare the matching Manager recovery inputs first. Failed or interrupted restores preserve their new candidate and require inspection through existing Manager recovery guidance.

An observed UFW default-deny policy is reported separately as `firewallPolicyObserved`; `firewallVerified` remains false. A successful endpoint observation does not establish firewall, deployment, rollback or recovery completion.

## Current verification scope

Nine source regression cases cover plan authority, consent, input refusal, binding and safe Manager commands, simulated host-key/transport faults, simulated DNS/TLS/readiness outcomes, and full rollback receipt binding/refusal. They compile the actual generated remote script and execute its unsupported-OS refusal on the actual Mac before it reads remote inputs or invokes Docker. The transport, rollback and endpoint success cases use test doubles; generated scripts are syntax checked and their actual unsupported-OS refusal runs on the Mac. Full backup restore, health and selection outcomes have not been executed over SSH. No actual SSH connection or private key was used.

The existing T10-02 acceptance is unchanged: isolated Linux/VPS deployment twice, real host-key mismatch/interruption, DNS delay, TLS/firewall/health validation and rollback still need real qualification. These unit results are not evidence that those checks passed.

## Native remote maintenance jobs

The optional `backup`, `backup-jobs`, `update` and `update-status` commands use the same fresh one-shot SSH plan, known-host pin, OED credential references, approved Manager binary and protected source binding. Their private connection file has exactly `consent`, `connection`, `oed`, `maintenance`. No command text, private key bytes or reusable authority grant is accepted. The Node API is `maintenanceSsh(plan, {action, input, preserveVolumes, externalWritersQuiesced, appsClosed, signal})`.

- `backup`: `maintenance` contains exactly `maintenanceImage` (qualified `sha256:` image ID) and `keyPath` (an existing external 32-byte private key on the server). Explicit volume preservation, stopped external writers and closed applications are required. Calls the genuine Manager `create-backup` command; completed means its created-and-authenticated receipt was verified. The safe response includes only job/backup IDs, authenticated manifest SHA and preservation/writer flags. It never resumes writers automatically.
- `backup-jobs`: `maintenance: null`; returns at most 50 existing native jobs with IDs, state, stage, bounded error code and timestamps. No raw logs or archive/key paths are returned.
- `update-status`: `maintenance` contains exactly `profilePath`, `updatePath`, `updateSha256`, `operationId`, `expectedGeneration`. It observes the matching current signed intent without running an update. After a lost response, the same operation may be observed at a safe current authority generation greater than or equal to the reviewed generation; a different operation or future reviewed generation refuses. It returns the observed generation and never replays runtime work or claims fresh health/selection verification. Update mutation still requires exact generation under the native atomic fence. A stage alone is not proof of readiness or activation.
- `update`: adds exactly `artifactPath`, `stagingParent`, `pythonPath`, `sourceCommit` (40-character approved source commit), `maintenanceImage`, `exportParent`, `hostArchivePath`, `trustArchivePath`, `keyPath`, `pairBindingPath`, `hostExtractionPath`. These are existing protected native full-recovery inputs on the remote server, not client uploads. The original signed intent, full host/trust checkpoint and registered target must already exist. This wrapper does not provision/re-enroll signing authority or manufacture a backup/plan. Calls genuine `execute-full-update` with the exact operation/generation pair checked inside the native Store fence before staging or runtime mutation. Older executables that do not accept that pair refuse; there is no downgrade to an unbound command. Completion requires the native Updated intent, exact target image/schema health, activation receipt, cold selection and live candidate readiness.

The existing full-original `rollback` contract remains unchanged. A failed/expired intent or interrupted SSH operation requires existing status/recovery and full-original rollback guidance; network retry is not an automatic replay. Native backup/full-original rollback work has a trusted 30-minute command budget; full update has 40 minutes, each with a 60-second transport cleanup margin. Plan/status remain bounded separately. These limits are fixed by the adapter, not caller-controlled. Cancellation terminates transport and reports uncertainty, because remote work may already have started; it never claims remote jobs or migrations were undone. No volumes, failed candidates or authority history are deleted.

Qualification of these new wrappers uses generated-script syntax, actual unsupported-host refusal on the Mac and bounded synthetic native receipts. Actual remote backup/update/rollback, network resume, expiry and incompatible-database recovery remain NOT_RUN until an isolated supported server and its approved Linux Manager executable are qualified. No paid server or new credential is required for source checks.
