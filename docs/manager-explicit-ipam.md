# Explicit local IPAM adapter profile

This additive profile does not change OED v1. A caller explicitly requests a read-only network suggestion from a supporting pinned Manager CLI, prepares a **new** approved bundle with the chosen subnet/gateway, and independently approves new manifest/Compose/OED/executable hashes. It never edits an already approved installed root. The previous actual failed Start and its three retained volumes stay preserved.

The optional manifest `explicitLocalNetwork` is exactly `{mode:'explicit-rfc1918-v1',subnet:'10.240.0.0/28',gateway:'10.240.0.1'}` in the example only; the address must be chosen against current engine and actual host route observations, including VPN routes. Every /28 must be aligned within 10.240.0.0/16, with the first usable gateway. All other supported two-service Compose fields remain exact, and only `networks.default.ipam.config:[{subnet,gateway}]` is added. Any unknown field, wrong gateway or differing approved Compose refuses. The manifest/Compose/OED/executable hashes are still independently approved; presence of an image or an old binding does not grant permission.

Plan requires the approved executable to answer `--local-network-capabilities` with exactly `{version:1,mode:'explicit-rfc1918-v1',readOnlySelector:true}` under a bounded read-only invocation. An old or unsupported binary refuses before mutation, with no fallback. The Manager selector `--choose-explicit-local-network` runs before any LifecycleService/root/job recovery constructor and needs the explicitly pinned local DOCKER_HOST environment with context/TLS selectors removed. Selection is an observation, not an address reservation, and never modifies daemon settings or removes networks.

The opaque plan uses profile `manager-local-selfhost-v2-explicit-ipam` and binds the policy in its immutable private configuration record. The kernel repeats admission under its existing operation lock and verifies actual owned network metadata after mutation. Stop preserves its owned-data behavior. Linux exemptions apply only to the exact validated owned bridge's kernel/link route, not VPN, broader or different-interface routes. Local daemon/proxy trust and pointwise observations remain limitations.

The fixed adapter source `6d328f6e4c73f97dfe5999174659905ec61ba59c` passed 34 built-in Node tests, with zero failures. Its capability fixture is a synthetic executable and does not establish native engine behavior. Separately, fixed Manager source `3978a5f86e726452952ff17b47db71b731d03f88` passed offline cached release compilation, two focused policy tests and 364 core tests (35 ignored); its release CLI and pure capability response were verified. Actual IPAM install/start/readiness/reopen/restart and actual Linux route execution remain NOT_RUN. The preceding cached-image implementation passed its distinct tests and actual Install, while its Start failed with ENGINE_NETWORK_CAPACITY. Those earlier results are not evidence for this new source. T10-01 production/realtime/TLS/metrics/backup/rollback and original Manager recovery gates remain incomplete.
